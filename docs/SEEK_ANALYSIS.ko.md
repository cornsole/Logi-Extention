# YouTube 가로 휠 탐색 분석

기준 구현: `cd19078`  
측정 환경: Chromium + `dist/chrome` + YouTube Big Buck Bunny 4K, 일시정지 상태

이 문서는 반복 가로 휠 탐색 지연과 첫 오른쪽 입력 무반응 현상의 재현 데이터, 원인, 수정 기준을 기록한다.

## 1. 반복 입력 지연

### 측정 결과

| 입력 방식 | 탐색 요청 시작 | 새 프레임 또는 탐색 완료 |
|---|---:|---:|
| 짧은 가로 휠 입력 | 98ms | 170ms |
| 20ms 간격의 감속 입력 18회, 총 350.7ms | 443.3ms | 511ms |
| YouTube 재생바 클릭, 빠른 표본 | 거의 즉시 | 44~77ms |
| YouTube 재생바 클릭, 네트워크 지연 표본 | 거의 즉시 | 약 310ms |

300ms 간격으로 네 번 이동한 표본에서는 각 휠 입력 후 85~98ms에 탐색 요청이 시작됐고 새 프레임은 134~183ms에 표시됐다. 모든 탐색이 완료됐으므로 이전 `inFlight` 탐색이 다음 탐색을 막는 현상은 확인되지 않았다.

네 개의 미버퍼 휠 목표는 `videoplayback` 요청 8개를 발생시켰다. YouTube의 세 개 유효 재생바 클릭은 6개를 발생시켰다. 목표 하나당 요청 수가 증가한 증거는 없으며, 오디오와 비디오 요청 쌍으로 판단된다.

### 원인

미버퍼 목표는 마지막 휠 이벤트마다 80ms 후행 타이머를 다시 시작한다. MX Master의 관성 입력처럼 이벤트가 계속 들어오면 네트워크와 디코더가 느린 것이 아니라 `video.currentTime` 요청 자체가 계속 연기된다.

감속 입력 표본에서는 마지막 이벤트 후 탐색까지 92.6ms였지만, 최초 입력 기준으로는 443.3ms가 걸렸다. YouTube 재생바 클릭에는 이 인위적인 대기 시간이 없다.

### 수정 기준

순수 후행 디바운스를 최대 대기시간이 있는 하이브리드 방식으로 교체한다.

- 버퍼된 목표: 현재처럼 즉시 적용
- 미버퍼 목표: 마지막 입력 후 80ms 또는 최초 입력 후 100ms 중 먼저 도달한 시점에 최신 목표 적용
- 100ms 중간 적용 후 입력이 계속되면 미리보기만 갱신
- 입력이 끝났을 때 목표가 달라졌다면 최종 목표 한 번 적용
- 긴 제스처의 미버퍼 할당은 중간 목표와 최종 목표, 최대 두 번
- 재생 시작과 수동 재생바 조작 시 기존 flush/cancel 동작 유지

합격 기준:

- 첫 미버퍼 `currentTime` 할당이 최초 입력 후 150ms 이내
- 최종 할당이 마지막 입력 후 100ms 이내
- 긴 제스처당 미버퍼 할당 최대 2회
- 새 제스처가 이전 타이머나 완료 이벤트에 막히지 않음

## 2. 첫 오른쪽 입력 무반응

### 재현 결과

기본 설정은 `inverted: true`, 시작 위치는 0초다.

| 입력 | 결과 |
|---|---:|
| 첫 `deltaX +1000` | 0초, 이동 없음 |
| 이어서 `deltaX -1000` | 20초로 이동 |
| 다시 `deltaX +1000` | 0초로 이동 |

### 원인

현재 변환식은 `inverted: true`일 때 양수 `deltaX`를 음수 시간으로 바꾼다. 0초에서 음수 목표는 탐색 하한인 0초로 clamp되므로 첫 오른쪽 입력이 무시된 것처럼 보인다. 왼쪽 입력으로 20초까지 이동한 뒤에는 오른쪽 입력이 0초 방향으로 이동할 공간이 생겨 동작한다.

초기화 실패나 첫 이벤트 유실이 아니라 기본 방향 매핑과 탐색 하한이 결합된 결정적 동작이다.

### 수정 기준

MX Master 기본값인 `inverted: true`에서 양수 `deltaX`가 앞으로 이동하도록 기준 부호를 바로잡는다. 체크박스는 계속 두 방향을 전환하며, 감도 슬라이더의 가로 휠도 같은 매핑을 사용한다. 세로 휠 방향은 변경하지 않는다.

합격 기준:

- 기본 설정과 0초 위치에서 `deltaX +1000`이 20초로 이동
- 이어지는 `deltaX -1000`이 다시 0초로 이동
- 방향 반전을 끄면 위 결과가 정확히 반대
- 감도 슬라이더에서 기본 가로 오른쪽 입력은 증가, 왼쪽 입력은 감소
- 세로 휠의 증가·감소 방향은 기존과 동일

## 3. 수정 후 실제 브라우저 검증

화면에 표시된 Chromium의 실제 YouTube 플레이어에서 최종 구현을 측정했다. 백그라운드·headless 탭은 브라우저가 타이머와 `requestAnimationFrame`을 제한하므로 지연 합격 판정에서 제외했다.

| 검증 항목 | 결과 |
|---|---:|
| 기본 설정, 0초에서 `deltaX +1000` | 20초 |
| 이어서 `deltaX -1000` | 0초 |
| 긴 미버퍼 제스처의 첫 할당 | 최초 입력 후 109.9ms |
| 긴 미버퍼 제스처의 최종 할당 | 마지막 입력 후 83.2ms |
| 긴 미버퍼 제스처의 총 할당 | 2회 |

첫 로딩 요청은 기존 감속 입력 표본의 443.3ms에서 109.9ms로 줄었다. 최종 할당은 후행 80ms 타이머와 한 프레임 이내의 스케줄링 비용을 포함해 83.2ms였다.
