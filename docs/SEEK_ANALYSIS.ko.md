# YouTube 가로 휠 탐색 분석

기준 구현: `cd19078`  
측정 환경: Chromium + `dist/chrome` + YouTube Big Buck Bunny 4K, 일시정지 상태

이 문서는 반복 가로 휠 탐색 지연과 첫 오른쪽 입력 무반응 현상의 재현 데이터, 원인, 수정 기준을 기록한다.

## 1. 반복 입력 지연

### 측정 결과

| 입력 방식 | 탐색 요청 시작 | 새 프레임 또는 탐색 완료 |
|---|---:|---:|
| 짧은 가로 휠 입력 | 98ms | 170ms |
| 20ms 간격의 감속 입력 18회, 총 350.7ms | 443.3ms | 511ms |
| YouTube 재생바 클릭, 빠른 표본 | 거의 즉시 | 44~77ms |
| YouTube 재생바 클릭, 네트워크 지연 표본 | 거의 즉시 | 약 310ms |

300ms 간격으로 네 번 이동한 표본에서는 각 휠 입력 후 85~98ms에 탐색 요청이 시작됐고 새 프레임은 134~183ms에 표시됐다. 모든 탐색이 완료됐으므로 이전 `inFlight` 탐색이 다음 탐색을 막는 현상은 확인되지 않았다.

네 개의 미버퍼 휠 목표는 `videoplayback` 요청 8개를 발생시켰다. YouTube의 세 개 유효 재생바 클릭은 6개를 발생시켰다. 목표 하나당 요청 수가 증가한 증거는 없으며, 오디오와 비디오 요청 쌍으로 판단된다.

### 원인

미버퍼 목표는 마지막 휠 이벤트마다 80ms 후행 타이머를 다시 시작한다. MX Master의 관성 입력처럼 이벤트가 계속 들어오면 네트워크와 디코더가 느린 것이 아니라 `video.currentTime` 요청 자체가 계속 연기된다.

감속 입력 표본에서는 마지막 이벤트 후 탐색까지 92.6ms였지만, 최초 입력 기준으로는 443.3ms가 걸렸다. YouTube 재생바 클릭에는 이 인위적인 대기 시간이 없다.

### 수정 기준

순수 후행 디바운스를 최대 대기시간이 있는 하이브리드 방식으로 교체한다.

- 버퍼된 목표: 현재처럼 즉시 적용
- 미버퍼 목표: 마지막 입력 후 80ms 또는 최초 입력 후 100ms 중 먼저 도달한 시점에 최신 목표 적용
- 100ms 중간 적용 후 입력이 계속되면 미리보기만 갱신
- 입력이 끝났을 때 목표가 달라졌다면 최종 목표 한 번 적용
- 긴 제스처의 미버퍼 할당은 중간 목표와 최종 목표, 최대 두 번
- 재생 시작과 수동 재생바 조작 시 기존 flush/cancel 동작 유지

합격 기준:

- 첫 미버퍼 `currentTime` 할당이 최초 입력 후 150ms 이내
- 최종 할당이 마지막 입력 후 100ms 이내
- 긴 제스처당 미버퍼 할당 최대 2회
- 새 제스처가 이전 타이머나 완료 이벤트에 막히지 않음

## 2. 첫 오른쪽 입력 무반응

### 재현 결과

기본 설정은 `inverted: true`, 시작 위치는 0초다.

| 입력 | 결과 |
|---|---:|
| 첫 `deltaX +1000` | 0초, 이동 없음 |
| 이어서 `deltaX -1000` | 20초로 이동 |
| 다시 `deltaX +1000` | 0초로 이동 |

### 원인

현재 변환식은 `inverted: true`일 때 양수 `deltaX`를 음수 시간으로 바꾼다. 0초에서 음수 목표는 탐색 하한인 0초로 clamp되므로 첫 오른쪽 입력이 무시된 것처럼 보인다. 왼쪽 입력으로 20초까지 이동한 뒤에는 오른쪽 입력이 0초 방향으로 이동할 공간이 생겨 동작한다.

초기화 실패나 첫 이벤트 유실이 아니라 기본 방향 매핑과 탐색 하한이 결합된 결정적 동작이다.

### 수정 기준

MX Master 기본값인 `inverted: true`에서 양수 `deltaX`가 앞으로 이동하도록 기준 부호를 바로잡는다. 체크박스는 계속 두 방향을 전환하며, 감도 슬라이더의 가로 휠도 같은 매핑을 사용한다. 세로 휠 방향은 변경하지 않는다.

합격 기준:

- 기본 설정과 0초 위치에서 `deltaX +1000`이 20초로 이동
- 이어지는 `deltaX -1000`이 다시 0초로 이동
- 방향 반전을 끄면 위 결과가 정확히 반대
- 감도 슬라이더에서 기본 가로 오른쪽 입력은 증가, 왼쪽 입력은 감소
- 세로 휠의 증가·감소 방향은 기존과 동일

## 3. 수정 후 실제 브라우저 검증

화면에 표시된 Chromium의 실제 YouTube 플레이어에서 최종 구현을 측정했다. 백그라운드·headless 탭은 브라우저가 타이머와 `requestAnimationFrame`을 제한하므로 지연 합격 판정에서 제외했다.

| 검증 항목 | 결과 |
|---|---:|
| 기본 설정, 0초에서 `deltaX +1000` | 20초 |
| 이어서 `deltaX -1000` | 0초 |
| 긴 미버퍼 제스처의 첫 할당 | 최초 입력 후 109.9ms |
| 긴 미버퍼 제스처의 최종 할당 | 마지막 입력 후 83.2ms |
| 긴 미버퍼 제스처의 총 할당 | 2회 |

첫 로딩 요청은 기존 감속 입력 표본의 443.3ms에서 109.9ms로 줄었다. 최종 할당은 후행 80ms 타이머와 한 프레임 이내의 스케줄링 비용을 포함해 83.2ms였다.

## 4. 광고 탐색과 본편 상태 분리

### 확인된 위험과 이전 검증의 범위

기존 구현은 광고와 본편이 같은 `<video>`를 재사용할 때 대기 휠 입력, 타이머, 재생 시작 리스너와 프리뷰의 소유권을 충분히 구분하지 않았다. 광고 전체 차단 버전에서는 실제 건너뛰기 이후 `paused: false`와 1.2초 동안 1.127초의 본편 시간 증가를 확인했다. 다만 이것만으로 원래 재생 정지 증상의 직접 원인이 특정 콜백이라고 확정할 수는 없다.

### 세션 분리 방식

- 세션은 영상 요소, 세대 번호, 광고 상태와 미디어 소스를 구분한다.
- 같은 요소와 blob URL을 재사용해도 `emptied`·`loadstart`가 발생하면 이전 세션을 폐기한다.
- 광고 시작·종료, 영상 요소·소스 교체 시 대기 입력, animation frame, 탐색 타이머, 이벤트 리스너와 프리뷰를 정리한다.
- 비동기 콜백은 실행 직전에 세션을 확인하며, 이전 세션 작업은 새 세션의 목표나 프리뷰를 수정하지 않는다.
- 광고에는 실제 유효한 `seekable` 범위만 사용한다. 광고 길이만 보고 탐색 가능하다고 판단하지 않는다.
- 광고→본편 전환 시 기존 목표를 flush하거나 시간을 되돌리지 않으며, 강제로 `play()`·`pause()`하지 않는다.
- 광고 세션 분리 작업에서는 탐색 스케줄링을 변경하지 않았다. 이후 스케줄링 개선은 5장에 기록한다.

### 검증 기준

실제 제공된 광고에서 양방향 휠 입력, 입력 직후 건너뛰기, 본편의 시간 증가와 이후 정상 탐색을 측정한다. 광고 클래스 삽입이나 가짜 건너뛰기로 실제 광고 검증을 대체하지 않는다. 타이머와 완료 이벤트가 전환 뒤 늦게 도착하는 경합은 결정적 회귀 테스트로 검증한다.

### 실제 광고 검증 결과

화면에 표시된 Chromium에서 실제로 제공된 YouTube 광고로 측정했다. 자동 테스트는 65개 모두 통과했다.

| 시나리오 | 결과 |
|---|---|
| 탐색 가능한 광고(`seekable` 0~15.041초)에서 오른쪽 입력 | 1.81초 → 3.88초 |
| 이어서 왼쪽 입력 | 3.88초 → 1.89초 |
| 광고 종료 직전 입력 후 다음 광고로 전환 | 다음 광고가 0초부터 시작, 이전 광고 목표 미적용 |
| 광고에서 휠 입력 직후 건너뛰기 클릭 | 본편에서 `seeking` 0회, 0초부터 재생 |

| 본편 전환 후 오른쪽 입력 | 13.72초 → 34.11초, 재생 유지 |

## 5. 클릭 대비 가로 휠 탐색 지연

기준 구현: `6d33660`. 화면에 표시된 Chromium, Big Buck Bunny 4K, 일시정지 상태. 입력 시각은 `pointerdown`·`wheel` 이벤트의 `timeStamp`, 프레임은 `requestVideoFrameCallback`으로 측정했다.

### 원인

| 구성 요소 | 지연 |
|---|---:|
| 미로딩 목표의 후행 대기 | 80ms |
| 휠 입력 묶음 처리용 animation frame | 최대 약 16ms |
| 미디어 요청과 디코딩 | 클릭과 동일 |

YouTube 재생바 클릭은 목표 위치를 즉시 요청한다. 가로 휠은 미로딩 목표마다 80ms 동안 추가 입력을 기다린 뒤 요청했고, 긴 제스처에서는 100ms 중간 요청 후 입력이 끝날 때까지 다시 요청하지 않았다.

### 수정

- 제스처의 첫 미로딩 목표는 즉시 요청한다.
- 이후 입력은 마지막 요청으로부터 50ms가 지난 시점에 최신 목표만 요청한다.
- 일시정지 중 로딩된 목표는 기존처럼 즉시 갱신한다.
- 80ms 무입력 타이머는 요청 시작이 아니라 제스처 종료 정리에만 사용한다.

### 측정 결과

| 시나리오 | 수정 전 요청 시작 | 수정 후 요청 시작 | 수정 전 최종 프레임 | 수정 후 최종 프레임 |
|---|---:|---:|---:|---:|
| 미로딩 단일 휠 입력 | 102.1ms | 24.4~27.1ms | 255.4ms | 114.4~155.9ms |
| 미로딩 연속 입력 15회, 마지막 입력 기준 | 99.2ms | 45.8ms | 348.6ms | 289.1ms |
| 로딩된 연속 입력 15회, 마지막 입력 기준 | — | 26.7~28.0ms | — | 115.3~131.6ms |
| YouTube 재생바 클릭, 미로딩 | 30.6~41.3ms | 동일 | 143.3~265.5ms | 동일 |

단일 입력은 클릭과 같은 수준이 됐다. 연속 미로딩 입력은 중간 위치를 계속 요청하므로 요청 수가 5회에서 8~11회로 늘었고, 최종 프레임은 여전히 클릭보다 늦을 수 있다.

## 6. 재생 중 큰 가로 휠 입력의 버퍼링 반복

### 원인

재생 중에는 일시정지용 탐색 조정을 거치지 않고 animation frame마다 `currentTime`을 바로 변경했다. 큰 입력이 이어지면 이전 탐색이 끝나기 전에 새 탐색이 계속 시작되어 대부분 취소되고 버퍼링 이벤트가 반복됐다.

또한 재생 중 목표에 도달한 뒤에도 현재 시간이 계속 증가하므로, 최종 정리 단계가 이미 도달한 목표로 다시 탐색할 수 있었다.

### 수정

- 재생 중 입력도 같은 탐색 조정 경로를 사용한다.
- 재생 중에는 로딩 여부와 관계없이 첫 입력 즉시 요청, 이후 최대 50ms 간격으로 최신 목표를 요청한다.
- 이미 요청을 마친 목표는 현재 재생 시간과 비교하지 않고 완료로 처리한다.
- 재생 중에는 재생바 프리뷰를 표시하지 않는다.

### 측정 결과

| 입력 | 수정 전 탐색 요청 | 수정 후 탐색 요청 | 수정 전 버퍼링 | 수정 후 버퍼링 | 최종 위치 |
|---|---:|---:|---:|---:|---|
| 오른쪽 1000px × 10회 | 10 | 4 | 1 | 1 | 정상 |
| 왼쪽 1000px × 10회 | 7 | 3 | 4 | 3 | 정상, 0초에서 재생 |
| 오른쪽 300px × 30회 | 30 | 12 | 9 | 1 | 정상 |
| 좌우 방향 전환 1000px × 18회 | — | 8 | — | 1 | 정상 |

모든 수정 후 시나리오에서 입력 종료 후 재생이 계속 진행됐다.

## 7. 긴 연속 입력과 탐색 요청 설정

### 설정

팝업에서 다음 값을 직접 조절할 수 있다. 바뀐 값은 열린 YouTube 탭의 다음 휠 입력부터 적용된다.

|---|---|---:|---|

| 입력 종료 판단 | 20–300ms, 10ms 단위 | 80ms | 마지막 입력 뒤 제스처를 마무리하기까지 기다리는 시간 |

### 판단

- 화면에 보이는 탭에서는 긴 연속 입력의 최종 프레임이 클릭과 같거나 더 빨랐다. 연속 입력 중 앞선 요청이 목표 주변 구간의 로딩을 미리 시작한 것으로 추정한다(직접 측정하지 않음).
- 0ms는 요청이 가장 많고 최종 프레임도 가장 늦었다. 50–200ms 사이 차이는 시행 간 편차(클릭 89–441ms)보다 작아 기본값을 바꾸지 않았다.
- 장치나 네트워크에 따라 요청이 많아 버퍼링이 보이면 요청 간격을 늘리고, 최종 위치 확정이 느리게 느껴지면 입력 종료 판단을 줄인다.
- 이 측정은 일시정지 상태만 다룬다. 재생 중 결과는 6장의 Big Buck Bunny 측정이다.
